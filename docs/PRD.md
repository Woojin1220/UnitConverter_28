## 1. 개요

### 1.1 주제 (한 문장)

> **앞으로 어떤 단위 조합이 나올지 모르는 과제에서, 매번 검색·재확인 없이 변환 결과를 바로 얻어 제출 흐름이 끊기지 않게 한다.**

### 1.2 배경 — 진짜 문제

외울 수 없는 다양한 단위 조합 앞에서, 매번 찾아보느라 바로 답하지 못하고 **과제가 지연**된다.

### 1.3 페르소나

코딩 수업·과제에서 주어진 단위와 값을 다른 모든 단위로 변환해야 하는 **학습자**. 공식을 외우지 않으며, 새 단위 조합마다 방법을 다시 찾아본다.

---

## 2. R-G-I-O

| | 정의 |
|---|------|
| **Role** | 단위 변환 담당자 — `단위:값` 하나를 받아 나머지 모든 단위로 바꿔야 하는 사람 |
| **Goal** | 한 번의 입력으로 지원 단위 전체에 대한 정확한 변환 결과를 즉시 확인하고, 과제에 바로 쓸 수 있는 상태로 만든다 |
| **Input** | `단위:값` 문자열 (예: `meter:2.5`) |
| **Output** | 입력 단위를 제외한 모든 지원 단위에 대한 변환 결과 목록 |

**입력 예시**

```
meter:2.5
```

**출력 예시**

```
2.5 meter = 8.2 feet
2.5 meter = 2.7 yard
...
```

## 3. 성공 기준

| ID | 기준 | Mom Test 증거 |
|----|------|---------------|
| **SC1** | `meter:2.5` 입력 한 번으로 feet·yard 등 전 단위 변환 결과가 즉시 출력된다 | "방법을 찾아서 바꿨어" → 찾기 비용 제거 |
| **SC2** | 새 단위 추가 시 기존 변환 로직을 거의 건드리지 않고 전체 단위 변환이 동작한다 | "새 단위마다 찾아봐야 불편" → 반복 탐색·헷갈림 감소 |
| **SC3** | 변환·입력 검증이 테스트로 통과해, 제출 전 재계산·재확인이 필요 없다 | "과제지연" → 확인·지연 비용 감소 |

## 4. 기능 요구사항

### 4.1 Must Have (이번 세션)

| ID | 요구사항 |
|----|----------|
| **FR-1** | `단위:값` 형식 입력을 파싱한다 |
| **FR-2** | meter, feet, yard 간 변환을 meter 기준으로 계산한다 |
| **FR-3** | 입력 단위를 제외한 모든 지원 단위로 변환 결과를 출력한다 |
| **FR-4** | 음수, 잘못된 형식, 미등록 단위 입력을 거부한다 |
| **FR-5** | OCP를 만족 — 새 단위 추가 시 기존 코드 변경 최소화 |
| **FR-6** | SRP를 만족 — 입력 검증 / 변환 / 출력 책임 분리 |
| **FR-7** | 단위 변환 및 입력 검증 테스트 코드 작성 |

**비즈니스 로직**

- `1 meter = 3.28084 feet`
- `1 meter = 1.09361 yard`
- feet/yard 간 비율은 meter 기반으로 계산

| ID | 요구사항 |

### 4.3 Won't Have (이번 프로젝트에서 하지 않을 것)

| 항목 | 이유 |

| 앱·UI·검색 기능 우선 개발 | Pain은 프로그램 부재가 아니라 매번 찾기·확인·지연 |
| 모든 단위·공식 암기 전제 | Mom Test: "외우기 힘들다" 반복 — 일관된 변환 규칙에 위임 |
| JSON/CSV 등 부가 기능을 SC1~3 전에 우선 | 세션 핵심은 즉시·정확·재사용 |
| 미검증 가설 기반 기능 확장 | 지연 시간·감점 등 Mom Test 미확인 항목 |

## 5. 품질 요구사항

- **OCP:** 단위 추가 시 확장, 기존 코드 수정 최소화
- **SRP:** 클래스·모듈 단일 책임
- **TDD:** Red → Green → Refactor 루프로 변환·검증 로직 구현
- **입력 검증:** 음수, 잘못된 형식, 없는 단위 처리

## 6. 8계층 — 이번 세션 범위

### 6.1 Rule

```text
- Mom Test 진짜 문제: "매번 찾기 → 지연"을 줄이는 것이 1순위다.
- 변환 비율은 meter 기준으로 통일한다.
- 설계: OCP(단위 추가 시 확장), SRP(입력 검증 / 변환 / 출력 분리).
- 구현 전·후: 단위 변환·입력 검증 테스트를 작성한다.
- 입력 `단위:값` — 음수, 잘못된 형식, 미등록 단위는 거부한다.
```

### 6.2 Command

```bash
# 실행
python UnitConverter.py

# 테스트
pytest
```

### 6.3 Skill (AI 활용 시)

- TDD: Red(실패 TC) → Green(최소 구현) → Refactor(OCP/SRP)
- 리팩터: 단위 추가 시 "기존 클래스 수정"이 아닌 "등록/설정 추가"로 해결
- Mom Test 리마인더: "이 코드가 검색·재확인 시간을 줄이는가?" SC1~3에 대조

### 6.4 Test Loop

```text
[Loop 1 — 변환 정확성]  SC1, SC3
  RED  : meter→feet, meter→yard, feet→yard 등 기대값 assert
  GREEN: 기준 단위(meter) 경유 변환 구현
  REF  : 변환기 인터페이스·클래스 분리

[Loop 2 — 입력 검증]  SC3
  RED  : 음수, "abc", "unknown:1" 실패 TC
  GREEN: 파싱·검증 로직
  REF  : Validator 단일 책임

[Loop 3 — 확장성]  SC2
  RED  : 새 단위 등록 후 전체 변환 TC
  GREEN: OCP 충족 등록 방식 (설정/동적 등록)
  DONE : SC1~3 체크리스트 통과
```
